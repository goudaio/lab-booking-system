# 实验室设备预约系统 · 项目介绍文档

> 云枢小组 | 韩奕扬 · 艾子琦 · 米子东
> 最后更新：2026-10-25

---

## 一、这是什么

一个面向高校公共实验室的**设备预约与使用管理系统**。它解决的是"几十万的共享仪器，排期却靠微信群刷屏"这个真实困境，核心手段是把使用行为量化成**信誉分**，让"占了位置不来"第一次有代价。

**一句话**：零依赖、零构建的纯前端应用，双击 HTML 就能跑，数据存在浏览器本地。

---

## 二、它解决什么问题

高校公共实验室的大型设备多为全楼共用，排期长期依赖微信群口头报备与共享表格登记：

| 痛点 | 具体影响 | 现有做法的不足 |
|---|---|---|
| 信息不同步 | 重复安排或跑空趟，白耗通勤与样品准备时间 | 靠自觉更新，消息被淹没，表格无冲突校验 |
| 占而不用 | 稀缺机时空转，真正着急的人排不进 | 没有代价就没有约束，也不知谁常违约 |
| 故障不同步 | 到现场才发现设备坏了，严重时样品报废 | 状态与排期脱节，管理员不在就没人更新 |
| 利用率无数据 | 该不该再采购全凭感觉 | 数据不可聚合，做不了趋势对比 |

## 三、核心机制：信誉分

这是本项目区别于"一个普通 CRUD 表单"的地方。

```
初始 100 分
  按时完成使用      +5
  取消已确认预约    -5   （爽约）
  超时使用         -10

分数 < 60  →  冻结预约权限
           →  只能提交申诉
           →  管理员审核通过后，恢复至 60 分
```

配套的两个闭环：

- **报修闭环**：提交报修 → 设备立即转为"维修中"并**自动锁死他人预约** → 管理员处理 → 结果推送回报修人收信箱
- **申诉闭环**：低分用户申诉 → 管理员在"待审批申请"页审核 → 通过则恢复 60 分；拒绝须填原因，原因以通知送达

## 四、功能清单

### 通用

- 管理员 / 研究员**双角色**，登录后导航与可用页面完全不同
- 响应式布局，768px 断点适配移动端

### 设备

- 18 台设备，覆盖**物理 / 化学 / 生物 / 材料**四个学科
- 四种状态：可预约（绿）· 使用中（蓝）· 维修中（橙）· 已停用（红）
- 支持按名称/型号关键词搜索，按学科 / 分类 / 状态多重筛选

### 预约

- 开放**未来 14 天**，每天 4 个时段（08-10 / 10-12 / 14-16 / 16-18），可多选
- **冲突检测**：同设备同日期同时段不可重复预约
- 信誉分 ≥60 自动通过；<60 拦截并引导申诉

### 智能推荐 ⭐

目标时段被占满时，不是简单弹一句"已被预约"，而是给出**两条替代路径**：

- 同类学科中同时段空闲的**可替代设备**
- 本设备未来 14 天内**最近的可用日期**

结果可一键切换 —— 点标签直接跳到对应设备或日期继续预约。**纯规则实现，不联网、离线可用。**

### 数据与治理（管理员）

- 设备访问统计：当天 / 近三天 / 近一周 / 近一个月多维对比 + 访问排行
- **数据导出迁移**：JSON 全量备份（可导入还原）、预约明细 CSV（带 UTF-8 BOM，**Excel 打开中文不乱码**）

### 研究员视角

- 使用情况：预约统计、信誉分变动记录、设备使用频次排行、我的预约记录

## 五、技术架构

### 技术栈

原生 HTML + CSS + JavaScript。**无框架、无构建工具、无 npm 依赖、无后端。** 数据持久化靠浏览器 `localStorage`。

### 分层设计

```
┌─────────────────────────────────────┐
│  App 对象（视图层）                   │
│  · 模板字符串拼接 HTML                │
│  · innerHTML 全量重绘                 │
│  · 内联 onclick 绑定事件              │
│  · 7 个页面路由 + 模态框交互           │
└──────────────┬──────────────────────┘
               │ 调用
┌──────────────▼──────────────────────┐
│  Store 对象（数据层）                 │
│  · localStorage CRUD                  │
│  · 业务规则：冲突检测、信誉分、宜申诉   │
│  · 超时扫描、统计聚合                 │
└──────────────┬──────────────────────┘
               │
┌──────────────▼──────────────────────┐
│  localStorage（6 个键）               │
│  devices / bookings / accounts       │
│  session / credit / messages         │
└─────────────────────────────────────┘
```

分层的好处：**数据层变更只动 Store，视图层重绘只动 App**，两侧不互相污染。

### 定时任务

每 60 秒扫描一次超时预约，自动标记为"已超时"并扣 10 分。

## 八、质量保障

### 自动化测试

项目带一套 35 项冒烟测试，覆盖：种子数据、本地时区、XSS 转义、登录鉴权、预约冲突、信誉分钳制、报修闭环、申诉闭环、智能推荐、CSV 转义。**全部通过。**

### 已修复的三类缺陷

| 问题 | 症状 | 修复 |
|---|---|---|
| **UTC 时区错位** | 早上 8 点前"今天/近三天"统计口径整体偏移一天 | 新增 `_dateStr()` / `todayStr()`，一律改用浏览器本地时区格式化；数据版本 v2→v3 强制重播种 |
| **XSS 注入** | "用途 / 报修描述 / 申诉理由"等字段可注入 `<script>` | 新增 `App.esc()`，13 处用户输入插值点全部转义 |
| **输入无约束** | 文本字段无长度限制、关键字段非必填 | 新增 `TEXT_LIMITS` 校验 + 表单 `maxlength` |

## 九、已知边界

诚实说明这套系统**目前不是什么**，这比吹它能做什么更重要：

1. **单机数据** —— `localStorage` 是单机单浏览器存储。换台电脑数据没了，两个人也看不到彼此的预约，冲突检测只在本地生效。它的准确定位是**高保真原型**，不是可部署上线的系统。
2. **信誉分是"君子协定"** —— 没有服务端裁判的前提下，用户打开 F12 改一个数字就能把 50 分改成 100 分。这套机制在"同设备、无对抗行为"的范围内成立，要真正落地必须补后端。
3. **契机决定它是原型** —— 正因为第 1、2 条，本项目衍生出了《智能体场景设计书》，描述它在具备服务端能力后的完整形态。

## 十、部署（可选）

### 华为云 OBS 静态托管

1. 创建 OBS 桶，权限设为"公共读"
2. 上传 `index.html`、`css/style.css`、`js/store.js`、`js/app.js`（**保持目录结构**）
3. 配置静态网站托管，默认首页设为 `index.html`
4. 修改 Content-Type：`.html` → `text/html`、`.css` → `text/css`、`.js` → `application/javascript`
5. 访问 `https://{桶名}.obs-website.{区域}.myhuaweicloud.com`
